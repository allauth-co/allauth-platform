# AllAuth engine migration

<!-- cspell:ignore OAEP -->

The project migration uses the existing PostgreSQL schemas, project IDs, key derivation and auth URLs. The React SDK and signed app proxy can be upgraded separately. A verified signed proxy request that omits the optional client IP keeps the client address supplied by the platform ingress. Production project requests and the shared issuer still use the existing engine.

## Verify in a development realm

Use an isolated PostgreSQL database, synthetic accounts and the verified accounts hostname for a development project. Add its immutable project ID from the registry to either setting. Both settings accept a comma-separated list of development project IDs and default to empty.

| Setting | Effect |
| --- | --- |
| `ALLAUTH_PROJECT_SESSION_SHADOW_IDS` | Compare the authenticated principal from successful project session responses with the AllAuth SQL reader. The comparison cannot authorize a request or change its response. |
| `ALLAUTH_PROJECT_HOSTED_UI_PROJECT_IDS` | Show the AllAuth React forms on the verified project accounts hostname. The forms read their capabilities from the selected authentication engine and use its session, broker and MFA handling. |

Use the hosted preview to exercise email and username password sign-in, registration, verification resend, password recovery, email links and codes, organization sign-in, configured social providers and passkeys. The dedicated MFA form supports authenticator and recovery codes and the existing trusted-device choice. The forms verify signed project OAuth continuations with the selected engine and preserve them across sign-in, email verification and MFA. Account selection, organization selection, invitation responses and consent use the same verified hosted realm. The hosted organization manager uses the first-party client for its session, organization, people, invitations and teams. The organization settings page preserves the existing name, slug, leave and deletion actions. The verified people, team, role and SSO management pages keep their scoped actions and use the selected project engine. First-party account pages cover profile edits, personal keys, passwords, provider links, sessions, passkeys, MFA and account deletion. Shared broker sign-in keeps its current path. Clear a project's ID from either setting to disable the corresponding preview.

The session comparison emits only the project ID and the result `match`, `different` or `unavailable`. A revocation that commits between the two reads can produce a difference. Review unexplained differences in the isolated fixture before using the reader for authorization.

## Measure a rollout cohort

Set `ALLAUTH_PROJECT_ENGINE_METRICS_IDS` to the same comma-separated immutable project IDs on the legacy baseline and candidate. The service emits one `allauth.project_engine_metrics` record per active project, writer, transport and operation in each process window. Export the records from every process once as NDJSON, with one event object per line. Select nonoverlapping UTC intervals during which you verified the respective writer revisions.

```sh
pnpm --dir apps/auth exec tsx scripts/compare-project-engine-metrics.ts /absolute/path/project-engine.ndjson \
  --project-id "$PROJECT_ID" \
  --legacy-start "$LEGACY_START_UTC" --legacy-end "$LEGACY_END_UTC" \
  --candidate-start "$CANDIDATE_START_UTC" --candidate-end "$CANDIDATE_END_UTC"
```

The comparison sums counts and histogram buckets for each operation and transport, and reports outcome rates and percentile bucket bounds. An `atMostMs` of `null` means the percentile is above the highest bound. Records that cross an interval boundary or name a different writer inside the interval appear in `excluded`. A group with a nonempty `missingWriters` list lacks observations for comparison.

The records cover sign-in and second-factor requests, provider callbacks, session reads and refreshes, and OAuth token exchanges and refreshes. HTTP redirects have a separate outcome, while known error redirects count as rejected. Compare these response outcomes with the realm's authentication event counts when assessing completed sign-ins. Check gateway and readiness evidence for requests that fail before engine dispatch, and exercise each verified accounts and frontend API hostname separately. The metric records contain the project ID and fixed labels and counts.

Baseline metrics also count the legacy project `/get-access-token` and `/refresh-token` operations on direct and hosted transports. The comparison shows these groups when it observes them. Investigate successful calls and confirm the project's configured clients before selecting its writer. Missing observations describe the sampled interval only.

The candidate preserves `/get-access-token` and `/refresh-token` for the owning session and exact local account ID. The direct project route accepts existing signed server session bearers and preserves session renewal, including `disableRefresh=true`. Browser and verified signed proxy calls use the owning cookie. Both responses use `Cache-Control: no-store`. The explicit refresh route retains the legacy response fields and writes encrypted grants with the stored scopes. The stock SDK proxy and hosted sign-in form allowlists omit these two operations. Isolated PostgreSQL checks cover Google and the project broker, concurrent account writes, credential rotation and rollback.

## Project cutover

- The AllAuth engine candidate covers password sign-in by email or username, registration, password recovery, email verification, session refresh and scoped session revocation in fixtures. Existing scrypt and Clerk bcrypt credentials still verify. Password recovery consumes legacy links and revokes project sessions, grants and outstanding challenges in the same transaction as the password change.
- When a project requires email verification, a valid email or username password sign-in for an unverified account returns `EMAIL_NOT_VERIFIED` and resends the verification link. Hosted links retain a live signed return to a registered project OAuth client. When the signed return expires before the email token, the AllAuth writer completes email verification and returns the user to the project account page. Directory-managed and directory-disabled accounts stay under directory authority and receive no resend from the AllAuth writer. The legacy writer could send those accounts a verification link before enforcing its directory session guard.
- First-party hosted password sign-in carries long signed project OAuth returns through authorization and consent. The verified accounts transport checks the exact signature, origin and registered app before completing the return.
- The stock project `/list-sessions` response preserves the owning account's active session records, freshness requirement and 100-record limit. The response omits stored session tokens on direct and hosted requests. The SDK session list and revocation contract uses session IDs.
- TOTP, recovery codes and trusted devices use existing project records and signed cookies. MFA enrolment and disable rotate the session and revoke sibling sessions and grants on a policy transition. Passkey HTTP ceremonies use SimpleWebAuthn with the existing credential IDs, counters, relying-party IDs and origins. PostgreSQL tests switch engines mid-ceremony and verify that the resulting session survives rollback. Guest passkeys keep the same identity and can complete an enrolled factor in either writer. The isolated tests also preserve an ordinary role and verification flag assigned to a guest after key enrollment.
- During pending MFA, a recovery-code check with `disableSession: true` consumes the code and attempt record. Both writers return the same user identity without creating a session or trusting the device. A fresh sign-in challenge can use another recovery code.
- The configured candidate uses the legacy active signing key and encryption versions when `BETTER_AUTH_SECRETS` is set. It keeps the derived project key for unversioned encrypted records. The restart rehearsal exercises versioned keys across sessions, provider callbacks and issuer signing.
- Existing Google provider secrets, project broker credentials and webhook signing secrets retain their original encrypted record format. PostgreSQL and signed delivery fixtures verify records written by either writer and read by the other. Disabling a saved direct Google client preserves its existing account links and sessions. An authorized operator can re-enable the client and users can resume sign-in with the same Google subject and project account.
- Magic links and sign-in codes consume the existing verification records, and both engines can complete an email proof issued by the other. Accounts with MFA enabled complete a second factor or prove a trusted device before receiving a session. Stored project domain and IP rules, credential-failure counters, and known-device cookies use the existing PostgreSQL records. Control counters and device cookies retain the derived project key when authentication sessions use a versioned key.
- Email verification and password recovery codes use the existing hashed PostgreSQL proofs and attempt budgets. Either engine can finish a code issued by the other. A successful code check leaves the proof available to consume. A completed password reset revokes access without issuing a session. The candidate enforces the realm's password-disabled policy on code issuance and password reset.
- Configured migration aliases resolve to the same verified project user ID for supported sign-in and recovery requests. Delivery goes to the saved account address. Public account creation and identity provisioning reserve the alias without using it to link an external identity.
- The configured project candidate exchanges codes with the existing AllAuth broker and the project's registered Google, Microsoft and Apple clients. Microsoft keeps the verified tenant and object-ID binding. Apple form returns and relay-email bindings survive switches between engines. Apple ID-token fixtures exercise Services ID and native bundle audiences while preserving the saved refresh grant's client binding. Unverified registrations receive verification mail through the project's approved callback. Fixtures verify pending broker callbacks across both engines and check that linked accounts retain their existing user IDs. Account linking and unlinking use the live project session. Organization creation, permission checks, active membership and invitation creation, acceptance and cancellation use the existing organization and session rows.
- Linked-account details use the exact saved account row and show only display fields from the configured provider. The candidate refreshes near-expiry grants with the existing encryption format and registered provider endpoints. A fresh owning session can unlink a historical provider or a credential row by its exact ID. The last saved account rule still applies. The candidate also declines removal of an enabled sign-in method if the remaining rows offer only disabled providers and the account has neither a registered passkey nor configured email sign-in.
- The read-only enterprise catalog counts stored SSO provider, SCIM credential and directory binding states in a single project schema. It reports configured records and credential expiry without exposing customer IDs or secrets. Exercise configured connectors with the current writer before changing a realm.
- The configured candidate handles SCIM public discovery and Users and Groups for established managed connections. A native credential stays valid after switching to AllAuth, and a credential rotated by AllAuth stays valid after rollback. It uses the existing bearer credentials and scopes, and preserves filtering, pagination and attribute projection. Managed User and Group writes preserve directory membership ownership, and User deactivation revokes sessions and grants when the last directory source is lost. The platform directory console and first-party hosted SSO page use the selected project writer to create connections, rotate and revoke credentials, and decommission directories. The hosted page returns the newly issued credential once to the authorized administrator. PostgreSQL fixtures resume the same retirement checkpoint in either engine, retain other active directory sources and revoke access when the last source is lost.
- Candidate logout and bulk session revocation revoke session-bound access and online refresh grants in the session deletion transaction. Offline refresh grants survive as before. Back-channel notices use the current project issuer and signing keys and are sent after commit. The hosted account switcher can activate and revoke sessions held by the same browser across either engine.
- Password, passkey, email link and email code sign-in, hosted social callbacks, verified native Apple sign-in, and email verification preserve the signed event when they replace a saved-device session. Successful sign-in removes the expired signed primary and returns the newly authenticated browser cookie. Enterprise OIDC, SAML and wallet sign-in name the active browser actor under required MFA and omit it under optional MFA. Required-MFA enterprise callbacks and direct Apple sign-in clean up an expired signed browser session even when the provider proof is rejected. Projects with an MFA or passkey subscription stay on the legacy writer when they require email verification or mandatory MFA. - Wallet sign-in verifies signed ERC-4361 messages with viem and preserves existing address and chain bindings. Both engines can consume the other’s pending nonce. ## Internal project selection

`ALLAUTH_PROJECT_ENGINE_INTERNAL_ID` allows one immutable development project in the protected AllAuth platform workspace to enter the pilot. The setting defaults to empty. Initial deployment readiness checks the registry and prepares the AllAuth engine for the signed proxy and the selected project's managed and active custom accounts and frontend API hostnames. These checks use the same writer revision and verify that the active hostname list stays stable. Activation builds fresh engines and checks compatibility against the current stored configuration. Readiness follows the restored writer after rollback. The admitted writer comes from PostgreSQL and starts at `legacy` revision `0`. When the admitted writer is `allauth`, new sign-in pages on both verified hostname types use the first-party forms.

Deploy the pilot-capable release with the exact project ID and confirm readiness. Before switching, confirm that the preceding deployment has drained and that each running replica uses the pilot-capable release with the same selection. A pilot-capable replica missing an active project selection fails readiness and declines that realm's requests. Check the configuration, signed proxy, default accounts and any active custom domains while the legacy writer is still active. Use the existing project session comparison and collect baseline route metrics for the same project ID.

For encrypted SAML evidence, run the following from a trusted checkout of the exact release with frozen dependencies and private database access. The TypeScript command is available in the source checkout. The standalone Docker and Railway runtime images do not include it. Supply the deployment's auth origin and secret, verified hosting settings, exact internal project ID and prepared legacy revision through the trusted operator environment.

```sh
pnpm --dir apps/auth exec tsx scripts/rehearsal/verify-project-encrypted-saml.ts PROJECT_SLUG PROVIDER_ID
```

Pipe one JSON object containing `receiver`, `samlResponse` and `relayState` to stdin from an approved test-account sign-in, while the native response is still pending. The `receiver` is the exact configured ACS URL. The command checks the protected legacy writer and current provider configuration, verifies the signed encrypted response and reads the existing request records without consuming them. Its receipt contains the observed cipher and signature mode, realm and receiver, and a configuration fingerprint. It excludes the assertion, relay state, identity and keys. Let the original callback complete normally through the legacy writer to confirm acceptance.

An IdP administrator must separately confirm the exact application's policy revision and the algorithms and signing settings applied across its configured sign-in paths. Collect representative successful samples for the enabled transports and applicable key and policy variations. A receipt records one observation and grants no admission. The deployment operator can set `ALLAUTH_PROJECT_ENGINE_ENCRYPTED_SAML_APPROVAL` only after that policy has been verified. Supply a JSON object with `kind` set to `operator-verified-encrypted-saml-policy-v1`, the exact `projectId`, `schemaName`, `providerId`, `providerRecordId`, `receiver`, `legacyWriterRevision` and current keyed `configurationFingerprint`. Include the administrator-verified `policyRevision`, UTC `verifiedAt` and `expiresAt` within seven days, and each allowed `{ "cipher": "aes256-gcm", "signatures": "assertion" }` profile. Supported cipher values are `aes128-gcm` and `aes256-gcm`. Signature values are `assertion`, `response` and `both`, subject to the saved assertion-signature requirement.

Verify readiness with the same settings in every release replica. The writer command rechecks the approval window, current SAML configuration and exact receiver under the writer admission lock. Once the matching AllAuth writer revision is active, it continues to check the stored provider and wire profile. The preparation deadline does not stop that writer's valid sign-ins. Configuration or receiver drift stops the affected candidate flow. Rollback is available even after the preparation deadline. A later activation requires approval for the new legacy revision. No live provider has been enrolled by this rehearsal.

Run the following commands from the application directory in the release container using the deployment database role.

```sh
node scripts/project-engine-writer.mjs status
node scripts/project-engine-writer.mjs switch legacy 0 allauth
node scripts/project-engine-writer.mjs status
```

The switch waits for admitted requests and guarded database transactions to finish. The first switch installs guards for the protected realm and records the writer in the same transaction. The guards reject credential and authorization writes carrying a stale engine revision. Other realms continue using their existing runtime. A concurrent transition or lock timeout leaves the stored writer unchanged by the rejected command. Read the current writer and revision before deciding whether to retry.

For rollback, read the current revision and use it as the expected revision for the switch to `legacy`. For example, the first rollback uses `node scripts/project-engine-writer.mjs switch allauth 1 legacy`. Confirm the signed proxy, new hosted pages, existing sessions and all affected integrations after the switch. First-party forms already open retain their request transport while the pilot-capable release is running. Keep the same keys and leave the database migration installed. Switch the stored writer back to `legacy` before reverting to a release that predates the fence. To reactivate after rollback, set `ALLAUTH_PROJECT_ENGINE_INTERNAL_PREPARE_REVISION` to the restored legacy revision on the new deployment. Verify readiness and confirm the preceding deployment has drained before switching. The operator command requires the prepared revision to match the expected revision.

## Production project cohorts

Start production cohorts after the internal pilot passes. Confirm the exact production project and workspace IDs through the management surface, verify its configured flows on the legacy writer, and collect its baseline. Use the release container and deployment database role to register that project and read its writer revision.

```sh
node scripts/project-engine-writer.mjs register-production "$PROJECT_ID" "$WORKSPACE_ID"
node scripts/project-engine-writer.mjs --project "$PROJECT_ID" status
```

Registration pins the production realm to its current workspace and schema and leaves its writer unchanged. A repeated registration of the same binding is safe. Configure `ALLAUTH_PROJECT_ENGINE_PRODUCTION_REVISIONS` on each rollout-capable replica as a JSON object mapping each selected production project ID to its exact prepared legacy writer revision. The setting defaults to an empty selection. For a newly registered project at revision `0`, its entry has the form `{"00000000-0000-4000-8000-000000000002":0}` with the verified project ID in place of the example ID.

Register the project before starting the prepared deployment. Confirm its readiness, then drain all older replicas and wait for their admitted requests and database connections to finish before switching. Exercise the signed app proxy and each verified accounts and frontend API hostname while the legacy writer is still active. Switch one project at a time and check its identity, session and connected-application contracts before promoting another cohort. Replicas serve an active AllAuth writer only when their prepared legacy revision matches the one used for its activation.

```sh
node scripts/project-engine-writer.mjs --project "$PROJECT_ID" switch legacy "$LEGACY_REVISION" allauth
```

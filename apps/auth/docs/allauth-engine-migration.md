# AllAuth engine migration

The project migration uses the existing PostgreSQL schemas, project IDs, key derivation and auth URLs. The React SDK and signed app proxy can be upgraded separately. Production project requests and the shared issuer still use the existing engine.

## Verify in a development realm

Use an isolated PostgreSQL database, synthetic accounts and the verified accounts hostname for a development project. Add its immutable project ID from the registry to either setting. Both settings accept a comma-separated list of development project IDs and default to empty.

| Setting | Effect |
| --- | --- |
| `ALLAUTH_PROJECT_SESSION_SHADOW_IDS` | Compare the authenticated principal from successful project session responses with the AllAuth SQL reader. The comparison cannot authorize a request or change its response. |
| `ALLAUTH_PROJECT_HOSTED_UI_PROJECT_IDS` | Show the AllAuth React forms on the verified project accounts hostname. The forms read their capabilities from the selected authentication engine and use its session, broker and MFA handling. |

Use the hosted preview to exercise email and username password sign-in, registration, verification resend, password recovery, email links and codes, organization sign-in, configured social providers and passkeys. The dedicated MFA form supports authenticator and recovery codes and the existing trusted-device choice. The forms verify signed project OAuth continuations with the selected engine and preserve them across sign-in, email verification and MFA. Account selection, organization selection, invitation responses and consent use the same verified hosted realm. The hosted organization manager uses the first-party client for its session, organization, people, invitations and teams. The organization settings page preserves the existing name, slug, leave and deletion actions. The verified people, team, role and SSO management pages keep their scoped actions and use the selected project engine. First-party account pages cover profile edits, personal keys, passwords, provider links, sessions, passkeys, MFA and account deletion. Shared broker sign-in keeps its current path. Clear a project's ID from either setting to disable the corresponding preview.

The session comparison emits only the project ID and the result `match`, `different` or `unavailable`. A revocation that commits between the two reads can produce a difference. Review unexplained differences in the isolated fixture before using the reader for authorization.

## Measure a rollout cohort

Set `ALLAUTH_PROJECT_ENGINE_METRICS_IDS` to the same comma-separated immutable project IDs on the legacy baseline and candidate. The service emits one `allauth.project_engine_metrics` record per active project, writer, transport and operation in each process window. Aggregate the outcome counts and latency histogram counts across processes before comparing periods. The last histogram bucket counts requests above the highest reported bound.

The records cover sign-in and second-factor requests, provider callbacks, session reads and refreshes, and OAuth token exchanges and refreshes. HTTP redirects have a separate outcome, while known error redirects count as rejected. Compare these response outcomes with the realm's authentication event counts when assessing completed sign-ins. The metric records contain the project ID and fixed labels and counts.

## Project cutover

- The AllAuth engine candidate covers password sign-in by email or username, registration, password recovery, email verification, session refresh and scoped session revocation in fixtures. Existing scrypt and Clerk bcrypt credentials still verify. Password recovery consumes legacy links and revokes project sessions, grants and outstanding challenges in the same transaction as the password change.
- TOTP, recovery codes and trusted devices use existing project records and signed cookies. MFA enrolment and disable rotate the session and revoke sibling sessions and grants on a policy transition. Passkey HTTP ceremonies use SimpleWebAuthn with the existing credential IDs, counters, relying-party IDs and origins. PostgreSQL tests switch engines mid-ceremony and verify that the resulting session survives rollback.
- The configured candidate uses the legacy active signing key and encryption versions when `BETTER_AUTH_SECRETS` is set. It keeps the derived project key for unversioned encrypted records. The restart rehearsal exercises versioned keys across sessions, provider callbacks and issuer signing.
- Magic links and sign-in codes consume the existing verification records, and both engines can complete an email proof issued by the other. Accounts with MFA enabled complete a second factor or prove a trusted device before receiving a session. Stored project domain and IP rules, credential-failure counters, and known-device cookies use the existing PostgreSQL records.
- Email verification and password recovery codes use the existing hashed PostgreSQL proofs and attempt budgets. Either engine can finish a code issued by the other. A successful code check leaves the proof available to consume. A completed password reset revokes access without issuing a session. The candidate enforces the realm's password-disabled policy on code issuance and password reset.
- Configured migration aliases resolve to the same verified project user ID for supported sign-in and recovery requests. Delivery goes to the saved account address. Public account creation and identity provisioning reserve the alias without using it to link an external identity.
- The configured project candidate exchanges codes with the existing AllAuth broker and the project's registered Google, Microsoft and Apple clients. Microsoft keeps the verified tenant and object-ID binding. Apple form returns and relay-email bindings survive switches between engines. Apple ID-token fixtures exercise Services ID and native bundle audiences while preserving the saved refresh grant's client binding. Unverified registrations receive verification mail through the project's approved callback. Fixtures verify pending broker callbacks across both engines and check that linked accounts retain their existing user IDs. Account linking and unlinking use the live project session. Organization creation, permission checks, active membership and invitation creation, acceptance and cancellation use the existing organization and session rows.
- Linked-account details use the exact saved account row and show only display fields from the configured provider. The candidate refreshes near-expiry grants with the existing encryption format and registered provider endpoints. A fresh owning session can unlink a historical provider or a credential row by its exact ID. The last saved account rule still applies. The candidate also declines removal of an enabled sign-in method if the remaining rows offer only disabled providers and the account has neither a registered passkey nor configured email sign-in.
- The read-only enterprise catalog counts stored SSO provider, SCIM credential and directory binding states in a single project schema. It reports configured records and credential expiry without exposing customer IDs or secrets. Exercise configured connectors with the current writer before changing a realm.
- The configured candidate handles SCIM public discovery and Users and Groups for established managed connections. A native credential stays valid after switching to AllAuth, and a credential rotated by AllAuth stays valid after rollback. It uses the existing bearer credentials and scopes, and preserves filtering, pagination and attribute projection. Managed User and Group writes preserve directory membership ownership, and User deactivation revokes sessions and grants when the last directory source is lost. The platform directory console and first-party hosted SSO page use the selected project writer to create connections, rotate and revoke credentials, and decommission directories. The hosted page returns the newly issued credential once to the authorized administrator. PostgreSQL fixtures resume the same retirement checkpoint in either engine, retain other active directory sources and revoke access when the last source is lost.
- Candidate logout and bulk session revocation revoke session-bound access and online refresh grants in the session deletion transaction. Offline refresh grants survive as before. Back-channel notices use the current project issuer and signing keys and are sent after commit. The hosted account switcher can activate and revoke sessions held by the same browser across either engine.
- Guest accounts keep their existing IDs, signed sessions and restricted role. PostgreSQL restart tests exercise password upgrades, explicit guest deletion and OAuth upgrades when only the provider state cookie reaches the callback. Guest sessions created by either engine remain readable by the other.
- The candidate admits stored `mfa.*` subscriptions in projects with optional MFA and email verification disabled. Rehearsals continue MFA enrollment for existing unverified and guest sessions across both writers, preserve their account IDs and roles, and deliver signed MFA enrollment, verification, disable and recovery-code events through the existing worker. The webhook manager uses the derived project key for signing credentials even when the authentication signing key has rotated. Migration `020` fences endpoint creation, deletion and rotation alongside the selected writer and leaves outbox processing available to the worker. The policy API declines incompatible updates while the candidate owns a configured webhook. Required MFA, projects that require email verification, ambiguous credential or MFA records, and any other configured webhook subscriptions stay on the legacy writer.
- Wallet sign-in verifies signed ERC-4361 messages with viem and preserves existing address and chain bindings. Both engines can consume the other’s pending nonce. The rollback fixture accepts an AllAuth-created wallet session without marking the contact email verified. [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361)
- Server-only one-time session transfers use the existing hashed identifiers and one-minute expiry. Both engines can consume the other's transfers once, without setting a cookie. HTTP generation and browser verification stay disabled.
- Workspace administrators can list, create, ban and unban project users, change roles and revoke sessions. Workspace and realm administrators can remove project accounts with their existing authority. The candidate rechecks live authority inside each mutation, preserves Apple grant revocation during erasure, and records the administrator and target in the audit.
- Clerk imports preserve source identities, existing bcrypt passwords and native replay fingerprints. Dormant provider links remain readable with exact Clerk provenance and no stored provider credentials.
- Invitation imports preserve source IDs, timestamps, roles and pending status. The same dry run and replay rules apply in both engines. Importing historical invitations does not send email.
- The candidate preserves organization updates, deletion, leave, member listing, removal and role changes. Team creation, editing, deletion, rosters and active selection use the existing team and session records. Dynamic role writes preserve the permission delegation checks. Renaming an assigned role updates current membership and pending invitation references in the same transaction. Those operations protect the last owner and revoke only the affected organization grants. Deletion of an organization with configured SSO or active directory authority requires that configuration to be removed first.
- The candidate advertises personal API keys after validating the project's stored default key configuration. Direct and verified hosted routes preserve list, create, read, update and revoke across rollback. Organization-owned keys and custom server-side quotas still block candidate selection. Server-side verification and expired-key cleanup keep the existing scoped key records, permissions and usage counters. The browser routes keep both operations private.
- Profile-photo uploads reuse the existing storage adapter. Public draft URLs keep their application scope, and owned uploads keep their readiness and ownership checks. The profile still changes only when the user saves the draft.
- The configured candidate supports HTTPS OIDC sign-in with a stored client secret, using registered endpoints or discovery. Separate protocol fixtures cover private-key JWT with a deployment-provided key resolver. Signed service-provider-initiated plaintext SAML can use generated metadata or a stored custom document with one POST ACS. The custom receiver must be the exact project endpoint or a verified accounts hostname for the same immutable project. The service publishes the original XML and checks the saved signing key and advertised endpoint. Removing the hostname binding blocks further use. The isolated process switches pending direct and hosted requests between engines and preserves the receiving engine's trusted redirect rules. The candidate registers and updates supported providers, lists and deletes authorized provider records, redacts stored credential material and preserves DNS verification and directory-binding restrictions across rollback. Directory-managed sessions require an active SCIM connection and the exact configured IdP subject. The candidate preserves unmanaged organization assignment and leaves pending invitations available to their recipients.
- Project enterprise OIDC preserves standard authorization error codes and the stored return URL after validating the callback against the current provider and pending state. Provider-specific codes use `invalid_provider`. Upstream descriptions and error URLs stay out of the redirect. [OAuth 2.0 error response](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2.1) and [OpenID Connect error response](https://openid.net/specs/openid-connect-core-1_0.html#AuthError)
- A stored custom SAML metadata document can retain its `SingleLogoutService` entry byte for byte. The project keeps single logout disabled, including at the advertised receiver. Stored `idpInitiatedCallbackUrl` values retain their redirect precedence for signed service-provider callbacks and refused unsolicited responses. Each destination must pass the receiving realm's trusted-origin and callback-loop checks. IdP-initiated authentication remains disabled.
- Encrypted SAML is limited to the digest-pinned isolated fixture. Native registration and update persist the encryption flags, SP private key and optional passphrase. The IdP chooses the wire algorithms per assertion. A metadata certificate identifies the receiver key. An algorithm advertisement cannot establish which algorithm the IdP will send. The fixtures interoperate for AES-128/256-GCM with RSA-OAEP-MGF1P and inner, envelope or dual signatures. The receiver requires an RSA private key of at least 2,048 bits. Rehearsals cover clear PEM and passphrase-protected PKCS#8 PEM. A stored custom SP document also needs one explicit encryption certificate matching that key and the existing verified POST receiver. Legacy AES-CBC assertions, unverified encryption profiles and unsupported key formats stay outside candidate selection.
- Native upstream OIDC registration and update require a deployment key resolver or static provider key for `private_key_jwt`. The installed project service supplies neither. The upstream private-key resolver stays fixture-only. Project applications registered with the issuer can use `private_key_jwt` and retain their saved public JWKS and single-use assertion records across code exchange and refresh. The installed project issuer permits authorization code, refresh and the approved device grant. Its claim extension adds support-actor claims without registering a custom grant.
- The configured candidate reads the project support registration and current workspace authority. Console and signed application support can launch, authorize and exchange handoffs in either engine. The restart fixture launches on the old engine, authorizes and exchanges through AllAuth, and stops the resulting connected support session after rollback. Candidate direct impersonation, stopping and revocation preserve actor ownership, expiry and audit records. Realm-local administrator impersonation keeps its separate signed actor cookie and restores the original session in either engine. Browser session reads require fresh console authority or the exact registered, signed application origin. The session keeps its original expiry and cannot authorize ordinary project writes.
- Authenticated password changes verify existing scrypt or Clerk bcrypt credentials. When the caller requests revocation, the candidate replaces the active browser session and revokes its siblings. Profile edits preserve the existing public fields and avatar ownership checks. Email changes and confirmed account deletion accept links from either engine and keep live session and account boundaries. The Apple deletion fixture revokes a legacy encrypted grant using its original client and retains the account when the grant changes before erasure. Scoped backend credentials continue to read the project service directory without receiving credentials or private profile fields.
- The verified project administrator OpenAPI endpoint documents implemented browser operations. It requires a live realm administrator cookie and omits generated database schemas and routes outside the documented surface.
- The candidate relays signed project MFA through the existing shared broker. Project discovery and JWKS preserve the issuer URLs, signing keys and rotation grace. Fixtures exercise authorization and consent, code exchange, refresh, introspection, revocation, UserInfo, device approval and browser logout against the existing project records. OAuth and device admission share the persisted rate counters across switches. Connected-app consent reads, scope updates and deletion keep the existing user ownership, row format and rollback behavior. Client registration, editing, catalog reads, deletion and secret rotation preserve administrator and owner checks. Each engine accepts a confidential client secret rotated by the other, and the previous secret is rejected. Prelogin metadata is scoped to the client named in the signed authorization request. Remaining issuer claims, enterprise and account administration and configured integrations need verification before activation.

## Internal project selection

`ALLAUTH_PROJECT_ENGINE_INTERNAL_ID` allows one immutable development project in the protected AllAuth platform workspace to enter the pilot. The setting defaults to empty. Initial deployment readiness checks the registry and prepares the AllAuth engine for both the signed proxy and verified managed accounts hostname. Activation builds fresh engines and checks compatibility against the current stored configuration. Readiness follows the restored writer after rollback. The admitted writer comes from PostgreSQL and starts at `legacy` revision `0`. When the admitted writer is `allauth`, new sign-in pages on the verified accounts hostname use the first-party forms.

Deploy the pilot-capable release with the exact project ID and confirm readiness. Before switching, confirm that the preceding deployment has drained and that each running replica uses the pilot-capable release with the same selection. A pilot-capable replica missing an active project selection fails readiness and declines that realm's requests. Check the configuration, signed proxy, default accounts and any active custom domains while the legacy writer is still active. Use the existing project session comparison and collect baseline route metrics for the same project ID.

Run the following commands from the application directory in the release container using the deployment database role.

```sh
node scripts/project-engine-writer.mjs status
node scripts/project-engine-writer.mjs switch legacy 0 allauth
node scripts/project-engine-writer.mjs status
```

The switch waits for admitted requests and guarded database transactions to finish. The first switch installs guards for the protected realm and records the writer in the same transaction. The guards reject credential and authorization writes carrying a stale engine revision. Other realms continue using their existing runtime. A concurrent transition or lock timeout leaves the stored writer unchanged by the rejected command. Read the current writer and revision before deciding whether to retry.

For rollback, read the current revision and use it as the expected revision for the switch to `legacy`. For example, the first rollback uses `node scripts/project-engine-writer.mjs switch allauth 1 legacy`. Confirm the signed proxy, new hosted pages, existing sessions and all affected integrations after the switch. First-party forms already open retain their request transport while the pilot-capable release is running. Keep the same keys and leave the database migration installed. Switch the stored writer back to `legacy` before reverting to a release that predates the fence. To reactivate after rollback, set `ALLAUTH_PROJECT_ENGINE_INTERNAL_PREPARE_REVISION` to the restored legacy revision on the new deployment. Verify readiness and confirm the preceding deployment has drained before switching. The operator command requires the prepared revision to match the expected revision.

Rehearse the release selector using the normal runtime image and an isolated Docker database. The harness checks both hosted sign-in views, the signed app proxy, persisted selection after restart, saved sessions and legacy-readable writes. The migrated address signs in to the same account through the signed app proxy and verified accounts hostnames before the switch, after activation and after rollback. A connected application exchanges an authorization code on the legacy writer and rotates the same offline grant through activation and rollback. Each ID token keeps the issuer, account subject and signing key.

```sh
docker build --target runtime -f apps/auth/Dockerfile -t allauth-auth:internal-rehearsal .
pnpm --dir apps/auth exec tsx scripts/rehearsal/check-compiled-project-engine.ts \
  --internal allauth-auth:internal-rehearsal
```

## Compiled project rehearsal

From the repository root, build both standalone images and run the fixture:

```sh
docker build --target runtime -f apps/auth/Dockerfile -t allauth-auth:rehearsal-baseline .
docker build --target project-engine-rehearsal -f apps/auth/Dockerfile -t allauth-auth:rehearsal-candidate .
pnpm --dir apps/auth exec tsx scripts/rehearsal/check-compiled-project-engine.ts \
  allauth-auth:rehearsal-baseline allauth-auth:rehearsal-candidate
```

The script creates an internal Docker network and a synthetic PostgreSQL database. It provisions a development realm and a production sibling through the compiled service, stops the legacy writer, checks that its database connections have closed, and clones the database. The candidate image requires the exact development project and workspace IDs, its derived schema, and a nonce whose hash matches a row in the restored database. The same standalone entry point serves signed app-proxy requests and verifies gateway envelopes for a stored custom hostname. The fixture checks session continuity, password rotation, revocation, isolation and personal key reads, then restarts the normal image over the same restored database to check rollback. The normal release target ignores the synthetic rehearsal settings.

The Railway HTTPS rehearsals passed at revisions `e4b429f` and `3597a5a` with private PostgreSQL 18.6, one app replica and zero deployment overlap. The native writer stopped before the database restore. The candidate and rollback deployments stopped in sequence, with zero app database connections observed before each switch. Signed proxy and verified custom-domain checks passed through Railway ingress. All three app deployments and the private database deployment were stopped after verification.

The normal release image passed the fenced Railway rehearsal at `c3c5084`. The persisted writer advanced from legacy revision 0 to AllAuth revision 1 and back to legacy revision 2 after restart. The managed accounts hostname rendered the corresponding sign-in page, and direct signed proxy requests and verified custom accounts requests retained their sessions and key access. The revoked session stayed revoked. All scratch deployments were stopped and the database retained private-only access.

For another rehearsal, provision a dedicated `allauth-rehearsal-xxxxxxxx` Railway project with a single `staging` environment, `rehearsal-app` and private `rehearsal-db` services, and one temporary HTTPS app domain. Use separate synthetic secrets and clean source snapshots. The shared harness accepts `--railway /absolute/path/to/private-profile.json` for the fixture images and `--internal-railway /absolute/path/to/private-profile.json` for the normal release image. Use the `runtime` target for both source snapshots in the fenced rehearsal. The harness validates the project, services, profile permissions and single-writer settings before switching.

## Shared issuer cutover

After project cohorts pass, replace the shared issuer as a unit. Keep the issuer and endpoint URLs, client registrations, subjects, claims, signing keys, consent, grant lifetimes, refresh rotation, revocation and approved device flows. Test token and grant continuity across cutover and rollback. Run the OpenID Provider conformance suite and an independent security review before switching the shared issuer.

Remove the old engine, UI, packages and build tooling from the current distribution after the rollback window. Keep the readers required for existing data, upstream attribution and immutable SDK releases.
